# ソフトウェアレビューの視点

効果的なコードレビューと品質確保のための観点をまとめています。

## 1. コードレビュー・チェックリスト

### 正しさ

- **機能**: 意図した処理を正しく行うか。
- **エッジケース**: null / 空配列 / 大量データなどを扱えているか。
- **ロジック**: ビジネスロジックに破綻がないか。

### セキュリティ

- **脆弱性**: 典型的な脆弱性 (SQLi, XSS, CSRF など) がないか。
- **入力検証**: 外部入力のバリデーションとサニタイズを行っているか。
- **秘密情報**: ハードコードされた秘密情報がないか。
- **認可**: 権限チェックが適切か。

### 可読性・保守性

- **命名 (AI フレンドリー)**:
  - **振る舞い重視**: 関数名は「何をするか」を表現し、「どうやるか」は書かない。
  - **標準英語**: 一般的なソフトウェア用語を使い、SVO など文法も意識する。紛らわしい省略やスラングは避ける。
  - **文脈付き**: AI が理解しやすいよう十分な文脈を含める (例: `user_id` を `uid` としない)。
  - **動詞を明確に**: `fetch_user` / `get_user` / `load_user` など動詞を使い分ける。
  - **真偽値は疑問形**: `is_active`, `has_permission` のようにする。
  - **曖昧さ排除**: `data`, `info`, `temp` など汎用名は最小限に。
- **構造**:
  - **単一責任**: クラス / 関数が一つの役割に集中しているか。God Object / God Function を避ける。
  - **意味的な分割**: ドメインや振る舞い単位で分割されているか。
  - **凝集度**: クラス / モジュール内の要素が論理的に結びついているか。
- **複雑度**: 過剰に複雑でないか、単純化できないか。
- **コメント**:
  - **公開 API**: 言語慣習に従ったコメントを付与する (自明な場合を除く)。
  - **内部**: 複雑な箇所を適切に説明し、最新状態に保つ。
- **一貫性**: プロジェクトのコーディング規約に沿っているか。

### パフォーマンス

- **効率**: N+1 や過剰なネストなど明らかなボトルネックがないか。
- **資源使用**: メモリ・リソース使用量を把握しているか。
- **解放漏れ**: ストリーム / DB 接続 / ファイルハンドルを確実に閉じているか。

### テスト

- **カバレッジ**: 新規コードに自動テストがあるか。
- **質**: 振る舞いを検証するテストになっているか (単なるカバレッジ稼ぎでないか)。
- **シナリオ**: 成功・失敗・エッジケースを網羅しているか。

### ドキュメント

- **API ドキュメント**: API 変更時に更新されているか。
- **コメント**: 内部コメントが分かりやすく有用か。

## 2. PR 品質チェックリスト

PR 自体のレビューでは、以下のガイドラインを遵守しているか確認してください。

- PR 作成ガイドライン (knowledge/pr-creation-guidelines.md)

**重要確認ポイント**

- **説明**: WHY と WHAT が明示されているか。
- **検証**: 手動・自動の検証内容が具体的に書かれているか。
- **完全性**: UI 変更の場合はスクリーンショットや動画が添付されているか。
