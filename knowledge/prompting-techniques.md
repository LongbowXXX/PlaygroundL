# Copilot 向けカスタムプロンプト技法

VS Code で GitHub Copilot 用のカスタムプロンプトを作る際に有効なテクニックをまとめています。

## `#todos` を使ったタスク管理

### 課題

コンテキスト解析や複数ファイル生成、リンク検証など複数の工程が必要な場合、Copilot が工程を抜かしたり進捗を見失い、結果が不完全になることがあります。

### 解決策

プロンプト冒頭で `#todos` ツールを使ってタスクを登録し、最後に検証ステップを要求することで、構造化された実行を強制します。

### 手順

1. **タスク初期化**: 役割定義の直後に、`#todos` ツールで上位タスクをすべて登録するよう指示する。
   > [!IMPORTANT]
   > TODO 項目と作業ステップを一致させる。ズレがあると進捗確認で誤りが起きる。
2. **最終確認**: プロンプト末尾に「Final Check」セクションを置き、全 TODO 完了の確認を要求する。

### 例

```markdown
# Role: [Role Name]

## 📋 Task Initialization

1. **Step 1**: ...
2. **Step 2**: ...
3. **Validation**: チェックを実施
4. **Final Check**: Final Check セクションを確認

## ✅ Final Check

- [ ] すべての TODO が完了
- [ ] すべての要件を満たす
```

### 効果

- **可視性**: 「Todos」ビューで進行状況を確認できる。
- **抜け漏れ防止**: 複雑な作業でも工程抜けを抑制。
- **自己修正**: チェックリストに照らして自己検証を促す。

## 最新仕様のナレッジ取得

### 課題

Copilot の学習データにはカットオフがあり、最新の VS Code Copilot 機能やファイル形式を知らない場合がある。

### 解決策

生成前に公式 URL から最新ドキュメントを参照するよう明示的に指示する。

### 手順

1. **重要 URL の特定**: プロンプトに必要な仕様が載っているページを決める。
2. **前提セクションの追加**: 「PREREQUISITE: Knowledge Retrieval」などのセクションで、指定 URL を読むように強制する。

### 例

```markdown
## 🚨 PREREQUISITE: Knowledge Retrieval

1. https://code.visualstudio.com/docs/copilot/customization/prompt-files
2. https://code.visualstudio.com/docs/copilot/reference/copilot-vscode-features#_chat-tools
3. https://code.visualstudio.com/docs/copilot/customization/custom-agents
```

### 効果

- **正確性**: 最新スキーマや仕様に沿った生成ができる。
- **機能活用**: モデルが知らない最新機能も利用できる。

## 透明性と幻覚対策

### 課題

AI 生成物が「正しい前提」で扱われると、幻覚が見逃され重大なミスに繋がる。逆に軽微な誤りに過度に時間をかけることもある。

### 解決策

すべての生成ドキュメント冒頭に生成タグを付け、AI 草稿であることを明示する。

### 手順

1. **タグを定義**: `<!-- This document is generated by @AgentName -->` のような共通形式を決める。
2. **指示の埋め込み**: スキルやエージェント定義で「必ずこのタグを入れる」と明記する。
3. **Good Enough 思想**: ドキュメントを「ジュニアの下書き」として扱い、重要箇所のみ重点確認するよう促す。

### 効果

- **安全性**: 確認が必要であることを明示。
- **効率**: 完璧さより検証を重視するマインドセットに変える。
- **追跡性**: どのエージェントが生成したか識別できる。

## Stop and Ask (サーキットブレーカー)

### 課題

原因が特定できず推測で修正を繰り返す「空振りループ」に陥ることがある。

### 解決策

根拠が不十分なまま進めないよう、一定回数で **STOP** してユーザーに確認するルールを設ける。

### 手順

1. **停止条件の定義**: 例) 3 回試して原因不明、再現不可など。
2. **制約セクションの追加**: プロンプトに停止条件を明記し、「修正優先」の指示より強くする。

### 例

```markdown
## ⛔ Stop Condition

3 回試しても原因が特定できない、または仮定が多い場合:

1. 実行を停止
2. 試した内容と結果を報告
3. 追加情報をユーザーに尋ねる
```

### 効果

- **効率**: 無駄な試行を抑える。
- **安全**: 根拠の薄い修正でコードを壊すリスクを下げる。
- **協働**: 適切なタイミングで人間にバトンを戻す。

## 環境非依存のツール利用

### 課題

`tools` を固定すると、開発者ごとに異なる拡張・MCP が使えなくなり、存在しないツール名を誤って書く危険もある。

### 解決策

新規プロンプトやエージェント生成時は `tools` を明示しない。デフォルト挙動に任せ、利用可能なツールを環境から自動で使わせる。

**例外**: 既存の厳格な参照をコピーする場合は、同じ `tools` を保持してよい。

### 手順

1. `.prompt.md` や `.agent.md` で `tools: [...]` を書かない。
2. ツール制限が必要な場合は人間が明示的に設定する。

### 効果

- **柔軟性**: 新しいツール追加に自動で追従。
- **移植性**: 環境差異で壊れにくい。
- **拡張性**: IDE の全機能を活用できる。

## 高影響な設定の漸進的変更

### 課題

`.vscode/tasks.json` など大きな設定ファイルを一括生成すると、確認コストが高く部分採用が難しい。

### 解決策

**提案ループ** を採用し、設定を一つずつ提案して同意を得てから反映する。

### 手順

1. 項目を一つ選び提案する。
2. 理由を添えて「追加してよいか」を尋ねる。
3. 同意を得たら次の項目へ進む。
4. 最後に合意済みの内容だけをまとめて出力する。

### 効果

- **認知負荷の低減**: 確認すべき差分量を小さくする。
- **選択的採用**: 取捨選択しやすい。
- **安全性**: 大規模上書きによる事故を防ぐ。
