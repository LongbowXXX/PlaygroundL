# PR 作成ガイドライン

このプロジェクトの Pull Request (PR) の構造と記述要件を定義します。厳守することでレビュー効率とコード品質を維持できます。

## 1. タイトル形式

厳密な命名規則はありませんが、目的が一目で分かる **簡潔で明瞭** なタイトルにしてください。

## 2. 本文の必須事項

PR の本文は背景を残すための記録です。**なぜ (Why)** と **何を (What)** を明確に記載してください。

### 共通原則

- **30 秒ルール**: レビュアーが 30 秒以内に Why と What を把握できるようにする。
- **整理された箇条書き**: 長文は避け、箇条書きを多用する。
- **DRY 原則**: 不要な繰り返しや冗長な説明は避ける。
- **自明な変更は説明不要**: リネームや単純なロジック修正など、差分で明らかな変更は文章説明を省く。
- **重複禁止**: リンク先の課題に書いてある内容はここで繰り返さない。

### 構成

#### 1. 背景 (Why)

- **Issue へのリンク**: 対応する Jira/GitHub Issue を必ず紐付ける (例: `Fixes #123`)。
- **動機 / 背景**:
  - **DRY 原則**: 詳細が Issue にある場合はここでは省略する。
  - 重複を避け、レビュー負荷を下げる。
  - チケットとの差分や本実装特有の点のみ強調する。

#### 2. 変更内容 (What)

- **サマリ**: 変更点を箇条書きで高レベルにまとめる。差分の逐次説明は不要。
- **影響範囲**: 影響する機能面・技術面を明示する。
- **バグ修正の場合**:
  - **原因**: バグの因果関係を説明する (なぜ発生したか)。
  - **対策**: 修正で原因をどう解消したかを説明する。
  - **横展開確認**: 同種のパターンが他所に無いか確認する。
- **技術的判断**: 代替案があった場合は選択理由を記載する。
- **移行・非互換**: マイグレーションや設定変更、API 互換性への影響があれば明示する。

#### 3. 検証内容 (Proof)

- **カバレッジ**: 影響範囲と原因を網羅する検証を記載する。
- **手動確認**: 手順ではなく「何を確認したか」にフォーカスする。
  - _悪い例_: 「1. ボタン A をクリック 2. 5 秒待つ 3. ログ確認」
  - _良い例_: 「ボタン A クリックで正しい API 呼び出しと UI 更新を確認」
  - **複雑な手順**: 手順が長い場合はチケットに記載し、ここでは参照のみとする。
- **自動テスト**: 実行したテストと追加したテストを明記する。
- **スクリーンショット / メディア**: UI やビジュアル変更では **必須**。可能なら Before / After を添付。

#### 4. リスク

- 潜在的なリスクや副作用、特に注意してほしい箇所を記載する。

## 3. レビュー依頼前のセルフチェック

- [ ] タイトルが簡潔で明瞭か。
- [ ] 本文が上記構成を満たしているか。
- [ ] Lint / Format を実行したか。
- [ ] ローカルテストが成功しているか。
- [ ] 不要ファイル (ログ・一時ファイル等) を含んでいないか。
